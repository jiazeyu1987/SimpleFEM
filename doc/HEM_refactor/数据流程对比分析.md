# 数据流程文档对比分析：原始版 vs 重构版

## 文档位置
- **原始版**: `doc/HEM检测/data-flow.md`
- **重构版**: `doc/HEM_refactor/data-flow.md`

## 核心差异总结

### 1. 架构呈现方式

#### 原始版
- **单一文件架构**: 描述 `simple_roi_daemon.py` (2500+行单文件)
- **功能流程图**: 使用ASCII图展示功能模块和数据流
- **流程化描述**: 按处理步骤（1-11步）线性描述

#### 重构版
- **模块化架构**: 展示10个独立管理器类的协作
- **组件层次结构**: 明确的组件依赖关系
- **编排器模式**: 强调 `Orchestrator` 作为中央协调者

**关键差异**:
```
原始: 单体架构 → 简单直观的流程图
重构: 模块化架构 → 清晰的职责分离和组件边界
```

### 2. 波峰检测逻辑描述

#### 原始版
```python
# 简化的二选一逻辑
if hybrid_detection_enabled:
    hybrid_peaks = hybrid_peak_detection(...)
    green_peaks = [p for p in hybrid_peaks if p['color'] == 'green']
    red_peaks = [p for p in hybrid_peaks if p['color'] == 'red']
else:
    green_peaks, red_peaks = detect_peaks(gray_buffer, ...)
```

#### 重构版
```python
# 完整的三态逻辑（与实际代码一致）
if hybrid_enabled and roi1_enabled and len(roi1_buffer) > 0:
    # 情况1: 混合检测
    hybrid_green_peaks, hybrid_red_peaks, hybrid_info = ...
    green_peaks = hybrid_green_peaks
    red_peaks = hybrid_red_peaks

elif hybrid_enabled and roi1_enabled:
    # 情况2: ROI1数据不足，跳过检测
    pass  # 等待ROI1缓冲区积累数据

else:
    # 情况3: ROI2独立检测
    green_peaks, red_peaks = detect_peaks(...)
```

**关键差异**:
- 原始版文档**简化了逻辑**，遗漏了"ROI1数据不足"的中间状态
- 重构版文档**完整反映了三态逻辑**，与实际代码一致
- 这是因为重构时发现并修复了这个关键的逻辑bug

### 5. 状态机模型

#### 原始版
```
简单的阈值保护状态机:
INACTIVE → ACTIVE → INACTIVE
```

#### 重构版
```
完整的状态机模型:

1. 阈值保护状态机
   INACTIVE → ACTIVE → RECOVERING → INACTIVE

2. 波峰检测状态机
   检测模式选择:
   ├── 混合检测模式 (ROI1时机 + ROI2颜色)
   ├── 跳过检测模式 (ROI1数据不足)
   └── ROI2独立检测模式 (传统)
```

**关键差异**:
- 重构版增加了 `RECOVERING` 中间状态
- 明确了"等待恢复延迟"和"稳定性检查"两个阶段
- 波峰检测三态逻辑清晰可见

---

### 6. 性能和错误处理

#### 原始版
- 简要提及错误处理
- 基本的性能考虑

#### 重构版
- **三级错误处理策略**:
  ```
  组件级: Manager处理失败 → 降级到默认值
  帧级:   帧处理失败 → 跳过该帧继续
  会话级: 视频处理失败 → 清理资源继续
  ```

- **性能优化细节**:
  - 固定大小缓冲区防止内存泄漏
  - 增量统计算法避免历史数据存储
  - 异步缓存I/O（每50帧刷新）
  - 原子文件写入（临时文件+重命名）

- 原始版文档基于原始简化逻辑编写
